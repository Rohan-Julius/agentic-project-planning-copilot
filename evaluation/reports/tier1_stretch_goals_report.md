## 1. Selective plan regeneration

**What was built:**
- `POST /projects/{project_id}/plan/regenerate/sprint-plan` — regenerates only `sprint_plan`
  from the current epics/stories, leaving epics, stories, technical tasks, dependencies, and RAID
  untouched.
- `POST /projects/{project_id}/plan/regenerate/tasks-deps-raid` — regenerates `technical_tasks`,
  `dependencies`, and `raid` together (they're generated by one LLM call and are cross-referential,
  so partial regeneration of just one would risk dangling dependency IDs) from the current
  epics/stories, leaving epics, stories, and sprint plan untouched.
- Both endpoints load the current plan via `load_current_plan`, call the narrower existing
  generation helper (`_generate_sprint_plan` / `_generate_tasks_deps_raid`), apply the same
  deterministic citation-correction pass RAID items already got (`_correct_raid_citations`), save
  a new `PlanArtifactVersion`, and — critically — call `_reset_approval_if_needed`, which sets
  `WorkflowRun.final_approved = False` if it was `True`. This preserves §20.5 ("agents never
  export an unapproved plan as approved"): regenerating content after approval must force
  re-approval before that content can be exported as APPROVED again.

**Deliberately out of scope:**
- Epics and stories are **not** selectively regeneratable. They're the structural backbone that
  IDs for tasks, dependencies, RAID, sprint plan, and the traceability matrix all key off of;
  regenerating them in isolation would either orphan every downstream artifact or require
  cascading regeneration of everything else anyway — at which point it's just "regenerate the
  whole plan," which the pipeline already supports via the existing revision-cycle path. This is
  a scope boundary, not an oversight.
- No selective regeneration of *individual* RAID items, dependencies, or tasks (only "all of
  tasks+deps+RAID together" or "sprint plan alone"). Finer granularity wasn't worth the added
  complexity for a PoC.

**Evidence:**
- 4/4 unit tests pass (`tests/unit/test_planning_regeneration.py`), including an explicit test
  that `final_approved` resets to `False` after regeneration when it started `True`.
- Full backend fast suite: 380 passed, 8 deselected, 0 failures (up from 372 pre-Tier-1).
- Live verification (see §4 below): both endpoints confirmed working against a real,
  live-generated plan — not just a mocked one.

## 2. Requirement-change impact analysis

**What was built:**
- `GET /requirements/{requirement_id}/impact` — returns a `RequirementImpact` object
  (`requirement_id`, `epics`, `stories`, `technical_tasks`, `dependencies`) listing every plan
  artifact traceable back to that requirement.
- Fully deterministic — `compute_requirement_impact` (in `app/tools/validation_tools.py`) reuses
  the existing traceability matrix (`plan.traceability.rows`, built by
  `_build_traceability_matrix`) rather than re-deriving anything. It joins on `requirement_id`,
  then filters `plan.epics` / `plan.stories` / `plan.technical_tasks` / `plan.raid.dependencies`
  by the IDs the matching traceability rows carry. No LLM call, no new grounding surface, no new
  guardrail risk — it's a read-only projection of data the plan already contains and had already
  validated.
- Frontend: an expandable "Show impact" panel per requirement card in the requirement list,
  rendering the four artifact-family lists inline.

**Deliberately out of scope:**
- RAID items are **not** included in the impact result. The traceability matrix's rows link
  requirements → epics → stories → acceptance criteria → source references; RAID items (risks,
  assumptions, issues, dependencies-as-log-entries — not to be confused with the `Dependency`
  schema) aren't keyed to individual requirements in that matrix, so there's no deterministic join
  path to them without inventing one. Extending the traceability schema to cover RAID would be a
  bigger, separate change.
- This is impact analysis for a plan that already exists — it does not attempt to predict what
  *would* change if a requirement's text were edited (that would require a live LLM call and
  re-opens grounding/citation questions this PoC's citation guardrails are built around). It
  answers "what does this requirement currently touch," not "what would change if I edited it."

**Evidence:**
- 4/4 unit tests pass (`tests/unit/test_requirement_impact.py`) on the first attempt, covering:
  a full traced requirement, an untraced requirement (empty result, not an error), 404 when no
  plan exists yet, 404 for an unknown project.
- Pure deterministic Python — no live verification needed beyond the unit tests; there's no LLM
  in this code path to fail differently under real model output than under a mock.

## 3. Version comparison UI

**What was built:**
- `frontend/src/pages/VersionHistory.tsx` — a new page (route:
  `/projects/:projectId/plan/versions`) with two version-selector dropdowns backed by the
  existing `GET .../plan/versions` and `GET .../plan/versions/{version_id}` endpoints (both
  already existed from Day 23; this task only added the frontend). Selecting two versions renders
  a per-artifact-family diff summary (Epics / Stories / Technical tasks / Dependencies): added,
  removed, modified, unchanged counts.
- `frontend/src/utils/versionDiff.ts` — `diffById<T, K>(previous, next, idKey)`, a generic
  id-keyed diff utility.

**Deliberately out of scope:**
- The diff is **whole-object-equality based** (`JSON.stringify(a) === JSON.stringify(b)` per
  matched ID), not field-level. An item is reported as "modified" if *anything* about it changed,
  but the UI does not show *which* field(s) changed. A field-level diff view would be a
  reasonable follow-up but adds real UI complexity (nested diffing for lists-within-objects like
  acceptance criteria) that wasn't justified for a PoC-stage comparison feature.
- RAID and sprint-plan contents aren't diffed by this page (only Epics/Stories/Technical
  tasks/Dependencies) — RAID and sprint plan have looser internal identity (no stable ID scheme
  as clean as epic/story/task IDs) so a naive id-keyed diff would be noisy; left out rather than
  shipped half-working.

**Evidence:**
- `frontend/src/utils/versionDiff.test.ts`: 2/2 tests pass.
- Full frontend suite: `tsc -b` clean, `vite build` succeeds, `oxlint` exit 0, `vitest run` 62/62
  passed (includes the 2 new tests).

## 4. Live verification

`tests/integration/test_evaluation_regeneration_live.py::test_regeneration_live` (marked
`@pytest.mark.slow`) runs a real base pipeline (via the existing
`evaluation/scripts/run_day22_live_verification.py::main`) against real Ollama (`qwen3:4b-instruct`)
and Qdrant, then exercises both new regeneration endpoints against the resulting live plan.

**First attempt** (1h13m27s): failed with `"No plan exists yet for project '...' to regenerate
from"`. Root cause, found by reading the captured log: the base pipeline's Planning stage failed
twice in a row with truncated/invalid JSON from the stories-generation call (a genuine,
pre-existing small-model reliability issue — the model produced JSON cut off mid-string — unrelated
to any Tier 1 code), exhausting §20.1's one-retry budget and controlled-stopping the workflow
before a plan was ever saved. The real bug this exposed was in
`evaluation/scripts/run_regeneration_verification.py` itself: it blindly assumed the base run
always produces a plan. Fixed by adding an explicit `GET .../plan` status-code check with a clear
`RuntimeError` that distinguishes "base pipeline didn't produce a plan, rerun" from an actual
regeneration defect.

**Second attempt: PASSED** — `1 passed in 3361.56s (0:56:01)`. Base pipeline metrics from this
run (`evaluation/reports/day22_live_verification.md`): 35 requirements extracted, 11 epics, 18
stories, 100% traceability coverage, 0 coverage gaps, plan structurally valid, 34/34 citations
correct, 18/18 stories with story points.

**Honest caveat — the interesting part.** This run's `final_status` was itself `"ERROR"`: the
Reviewer agent's own call failed (`outcome: "ERROR"`, 59.5s), which controlled-stops the workflow
short of `WAITING_FOR_HUMAN_INPUT`. The Planning stage had already succeeded and saved a valid
plan *before* the Reviewer's error, so `GET /projects/{id}/plan` still correctly returned 200 —
which is exactly why the plan-existence guard (checking the endpoint directly, not string-matching
`final_status`) let the script proceed. But `POST /plan/approve` requires
`run.status == STATUS_WAITING_FOR_HUMAN_INPUT` (`app/api/plan.py`, confirmed by reading the
code), and a workflow that controlled-stopped in `"ERROR"` status never reaches that state — so
the live run's `client.post(".../plan/approve")` call almost certainly returned 409, and
`final_approved` was **never actually set to `True`** during this live run.

That means the test's `assert result["approval_status_after"] != "APPROVED"` passed for a
reason weaker than "regeneration correctly reset approval": the plan was never approved to begin
with. **What this live run genuinely confirms:** both regeneration endpoints work correctly
against a real, live-generated plan (not a mock), and version history grows correctly (≥3
versions: base + 2 regenerations). **What it does not confirm:** the live "was approved → got
regenerated → became un-approved" transition — that specific behavior is proven only by the
deterministic unit test (`test_regenerate_sprint_plan_resets_final_approved` in
`tests/unit/test_planning_regeneration.py`), which explicitly seeds `final_approved=True` and
asserts it flips to `False` after regeneration. The reset logic itself is a two-line, easy-to-
verify-by-inspection check (`if run.final_approved: run.final_approved = False`), so this gap is
noted for completeness rather than treated as a real risk — but it's reported here rather than
glossed over, consistent with this project's evaluation discipline throughout.

A third live run chasing a cleaner approval-reset transition (i.e. one where the base run's
Reviewer stage happens to succeed) was considered and declined: two live runs already cost ~2
hours of wall-clock CPU-only inference time, the reset logic is simple and already deterministically
tested, and re-running for one specific assertion's live coverage wasn't judged worth a third
~1-hour run.

### Follow-up: the Reviewer's error was a real, fixable bug — not just noise

An initial version of this report treated the base run's Reviewer error as a caveat to note and
move past. That was wrong — it was live evidence of an actual defect and deserved a real fix,
not just documentation. Root-caused by reproducing the Reviewer call directly (against an
already-persisted real plan in the dev DB + real Ollama, ~1 minute, instead of a full ~1-2 hour
pipeline rerun): the error is the same failure class already known from Planning's stories call
(see `app/agents/runner.py`'s `num_predict=8192` comment) — the model's JSON output gets cut off
by the output-length cap before it finishes, producing pydantic's `json_invalid` error
(`"EOF while parsing a string/value..."`). This is probabilistic (it depends on how verbose the
model's free-text fields happen to be for a given plan), which is why the direct repro succeeded
on its first attempt while the live pipeline run hit it.

The retry-once path (§20.1) existed but wasn't actually addressing this failure class: on
retry it just told the model "match the expected schema," which doesn't explain *why* the first
attempt failed or what to do differently — so a truncation-caused failure had no better odds of
succeeding on retry than the first attempt. Fixed in `app/agents/runner.py::run_agent`: the
retry-feedback prompt now detects the `json_invalid` error type specifically and tells the model
its previous response was cut off for length, asking it to keep free-text fields (descriptions,
rationale, recommended actions) to one or two sentences so the full JSON fits — rather than the
generic "match the schema" message, which doesn't fit a truncation failure. Added
`test_run_agent_truncated_json_retry_asks_for_shorter_text` in `tests/unit/test_agent_runner.py`
to lock in the new retry-prompt content. Full fast suite: 381 passed, 0 failures (up from 380).

This doesn't claim to eliminate the failure class outright — it's still a small, CPU-only local
model producing long structured output, and `num_predict` wasn't raised further (a prior,
deliberately-documented tradeoff: a bigger context/output budget measurably slows every call, not
just the ones that would have failed). What changed is that the retry now gives the model an
actionable reason to succeed on the second attempt instead of repeating the same generic
instruction that already failed once.
